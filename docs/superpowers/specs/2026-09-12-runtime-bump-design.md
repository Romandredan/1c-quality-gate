# Автоматический сдвиг закрепления движков: дизайн

Статус: **утверждено 12 сентября 2026**, к реализации в v3.8.0.

## Задача

Плагин закрепляет два внешних движка по версии и SHA-256: статический анализатор
`bsl-analyzer` (`assets/analyzer/runtime-manifest.json`) и сервер справки платформы
`bsl-context` (`assets/platform-context/runtime-manifest.json`). Закрепление осознанное:
движок, меняющийся между прогонами, делает вердикт гейта невоспроизводимым, поэтому
самообновление на машине пользователя отвергнуто и остаётся отвергнутым.

Цена закрепления — ручной сдвиг: сходить в GitHub API релиза, переписать суммы и размеры,
прогнать проверки. Оба проекта выпускаются почти ежедневно, и закрепление отстаёт:
на 12 сентября 2026 анализатор закреплён на 0.2.73 при последнем 0.2.79, сервер справки
на 0.16.0 при последнем 0.18.1.

Решение: автоматизировать сдвиг закрепления **в конвейере плагина**, где новая версия
проходит тесты и ревью до того, как доедет до пользователей. К пользователям обновление
приходит как сейчас, с релизом плагина, и ставится само при первом прогоне.

Вне задачи: MCP `v8std` (удалённый HTTP-сервер, версии на стороне клиента нет), `lxml`
(зависимость через pip), сигнал отставания в `gate-status`.

## Скрипт `tools/runtime-bump.mjs`

Один скрипт на оба движка, движок выбирается флагом `--engine analyzer|platform-context`.

Порядок работы:

1. Читает манифест движка, запрашивает список релизов GitHub API по `repo` из манифеста,
   берёт последний релиз без признаков `prerelease` и `draft`. Токен из `GITHUB_TOKEN`
   в окружении, если задан, идёт в заголовок запроса (в CI без него лимит API низкий).
2. Сравнивает версию релиза с закреплённой. Равна или старше — обновления нет.
3. Собирает цели по именам asset. У `bsl-context` имя архива и каталога внутри содержит
   версию, поэтому в его манифест добавляются поля `assetTemplate` и `dirTemplate` с
   подстановкой `{version}` в каждой цели; у `bsl-analyzer` имена постоянные, его манифест
   не меняется. Если шаблона в цели нет, имя берётся из поля `asset` как есть.
4. Сумму и размер берёт из поля `digest` каждого asset (`sha256:<hex>`) и поля `size`.
   Если у asset нет `digest`, скачивает файл и считает сумму сам.
5. Отказывается обновлять, если хотя бы одна цель манифеста в релизе отсутствует.
   Частично обновлённого манифеста не бывает: либо все цели, либо ни одной.
6. Переписывает манифест с сохранением порядка полей и комментария `_comment`.
7. Правит в `docs/INSTALL.md` фразы, утверждающие текущее закрепление (для анализатора
   «проверено на **X**» и пример конфига с `"version": "X"`, для сервера справки строку
   штампа `engine=bsl-context@X/...`). Остальные упоминания старой версии по репозиторию
   перечисляет в выводе как список файлов для ручного решения. Разделы истории переходов
   (`docs/false-positives-cfe.md`, `docs/analyzer-integration.md`) не трогает.

Режимы:

| Флаг | Действие | Код возврата |
|---|---|---|
| `--check` | только сообщить, есть ли новее | 0 нет обновления, 3 есть, 1 ошибка |
| `--apply` | переписать манифест и INSTALL.md | 0 обновлено или нечего обновлять, 1 ошибка |
| `--json` | машиночитаемый результат в stdout вместе с любым режимом | как у режима |

JSON результата: `engine`, `current`, `latest`, `updated` (bool), `targets` (ключ →
`asset`, `sha256`, `size`), `releaseNotes` (массив `{tag, publishedAt, body}` по всем
пропущенным версиям от закреплённой до новой, `body` обрезан до 4000 символов),
`mentions` (файлы с упоминанием старой версии, кроме отредактированных и истории).

Сетевой слой инжектируется (`fetchImpl`), как в `platform-context-bootstrap.mjs`, чтобы
тесты шли без сети.

## Проверка после сдвига

Скрипт сдвига сам ничего не запускает. Проверка — отдельные шаги workflow и релизного
чеклиста:

- `bsl-analyzer`: `node tools/analyzer-bootstrap.mjs` качает бинарник по новому манифесту
  и сверяет SHA-256; затем `node tools/analyzer-run.mjs --sentinel` на фикстуре плагина.
  Работает на Linux без установленной 1С.
- `bsl-context`: `node tools/platform-context-bootstrap.mjs --install-only` качает архив,
  сверяет SHA-256 и распаковывает. Запустить сервер без установленной платформы нельзя,
  тело PR говорит это прямо. Флаг `--install-only` добавляется, если его нет.
- Общие: `node tools/validate-package.mjs`, `node tests/run-tests.mjs`.

## Workflow `.github/workflows/runtime-bump.yml`

- Запуск: `schedule` раз в неделю (понедельник, 06:00 UTC) и `workflow_dispatch` с
  необязательным выбором движка.
- Матрица по двум движкам, задания независимы. На каждый движок своя ветка и свой PR:
  `chore/bump-bsl-analyzer` и `chore/bump-bsl-context`. Раздельно, потому что сдвиг
  анализатора требует A/B-прогона на корпусе по `docs/false-positives-cfe.md`, а сдвиг
  сервера справки нет.
- Шаги задания: checkout, node 20, python + lxml (для тестов), `runtime-bump --check`;
  при коде 0 задание завершается без изменений. При коде 3: `--apply --json`, затем
  проверки из раздела выше, затем создание или обновление ветки и PR.
- Ветка создаётся от `main` заново при каждом прогоне (`git checkout -B`), пуш с
  `--force-with-lease`: ветка принадлежит workflow, ручных коммитов в ней не ожидается.
  Если PR с этой head-веткой уже открыт, новый не создаётся: тело PR обновляется, ревью
  запрашивается повторно, чтобы уведомление пришло снова.
- Тело PR: таблица «было → стало» по версии, суммы и размеры по целям, release notes
  автора за пропущенные версии, результат sentinel (для анализатора) или пометка «сервер не
  запускался, нет платформы» (для сервера справки), список файлов с упоминанием старой
  версии, напоминание ревьюеру о A/B по `false-positives-cfe.md` для анализатора.
- PR назначается на владельца репозитория (`--assignee`) и запрашивает его ревью
  (`--reviewer`). GitHub шлёт письмо и push в мобильное приложение. Логин берётся из
  `github.repository_owner`, в workflow не зашит.
- `permissions: contents: write, pull-requests: write`.

Ограничение штатного токена. PR, открытый `GITHUB_TOKEN`, не запускает `validate.yml`,
поэтому bump-workflow прогоняет те же проверки сам, на ubuntu. Матрица Windows на такой
PR не идёт: для сдвига закрепления без изменения кода это приемлемо. Личный токен снял бы
ограничение, но GitHub не уведомляет автора о его собственных действиях, и уведомление о
PR пропало бы, а сам токен протухает. Выбор в пользу штатного токена.

Настройка репозитория руками, один раз: Settings → Actions → General → «Allow GitHub
Actions to create and approve pull requests». Без неё `gh pr create` падает; workflow
проверяет это первым шагом создания PR и печатает понятную ошибку с путём к настройке.

## Тесты

В `tests/run-tests.mjs`, секция «Сдвиг закрепления движков», с инжектированным `fetchImpl`
и фикстурами ответов GitHub API в `tests/fixtures/runtime-bump/`:

- выбор последнего релиза: `prerelease` и `draft` пропускаются, порядок в ответе не важен;
- сравнение версий: равная и более старая не считаются обновлением;
- сборка целей по `assetTemplate`/`dirTemplate` и по постоянному `asset`;
- отказ при отсутствии цели в релизе, манифест не переписан;
- сумма из `digest`, размер из `size`; `digest` без префикса `sha256:` отвергается;
- откат на скачивание и подсчёт суммы, когда `digest` отсутствует;
- переписанный манифест сохраняет `_comment`, порядок полей и проходит существующие
  проверки манифестов;
- правка INSTALL.md меняет только фразы текущего закрепления;
- `mentions` перечисляет файлы со старой версией и не включает историю;
- коды возврата `--check` и `--apply`, JSON-вывод.

В `tools/validate-package.mjs`: фраза о закреплении в `docs/INSTALL.md` совпадает с
версией в манифесте для каждого движка. Ловит расхождение, если манифест поправили руками.

Новые проверки live-тестом workflow не покрываются; YAML проверяется существующим
`validate-package` на синтаксис, если такая проверка есть, иначе не проверяется.

## Документация

- `docs/RELEASING.md`: раздел «Сдвиг закрепления движков»: что делает workflow, разовая
  настройка репозитория, что проверяет ревьюер PR (для анализатора A/B на корпусе,
  сравнение состава диагностик `rules list`, дописать раздел перехода в
  `false-positives-cfe.md` при расхождениях), что сдвиг закрепления — PATCH по таблице
  семантики, если находки те же.
- `docs/INSTALL.md`: одна фраза о том, что закрепление сдвигается автоматически через PR
  и почему не самообновлением.
- `CLAUDE.md`, раздел «Перед коммитом»: строка `node tools/runtime-bump.mjs --check`
  не добавляется, проверка сетевая; вместо этого упоминание в RELEASING.md.

## Что не делается

- Автообновление у пользователя. Противоречит принципу воспроизводимости вердикта.
- Сигнал отставания в `gate-status` и `--status` бутстрапов. Сетевой запрос в статусе
  не нужен, пока PR приходит сам.
- Сдвиг `analyzer.version` в проектных `.1c-quality-gate.json` пользователей. Проектное
  закрепление — осознанный выбор проекта, плагин его не трогает.
