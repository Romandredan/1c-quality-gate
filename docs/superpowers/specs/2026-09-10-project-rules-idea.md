# Идея: правила проекта, конвейер правил, правила из практики

Статус: **идея, дизайн не одобрен.** Обсуждение остановлено 10 сентября 2026, чтобы закончить
v3.6.0. Продолжить с раздела «Что осталось решить».

## Суть

Гейт применяет только правила, зашитые в плагин. Хочется, чтобы новые правила добавлялись без
правки плагина и не терялись находки, которые уже подтвердились на живом ревью.

Живой пример, ради которого это нужно: в одном из проектов нашли дефект «тело HTTP-ответа
читается сырым полем рядом с вызовами проектной HTTP-обёртки» — он повторялся ещё в двух десятках
методов соседнего расширения. В публичный плагин такое правило не годится (обёртка проектная),
а в проекте должно ловиться всегда.

## Три подзадачи, общее ядро

1. **Правила проекта.** Владелец кладёт правило в свой репозиторий, гейт его применяет.
   Здесь решается формат правила и откуда гейт его берёт — ядро для двух остальных.
2. **Конвейер добавления.** Одна команда создаёт правило целиком: карточку, пару, запись в
   реестре, тест. Работает и для плагина, и для проекта; сейчас это 5–6 файлов вручную.
3. **Правила из практики.** Подтверждённая владельцем находка превращается в заготовку правила
   через тот же конвейер. Пара берётся из самой починки: код до исправления — «дефект», после —
   «чисто».

Порядок: 1 → 2 → 3. Первая задаёт формат, вторая его производит, третья наполняет.

## Уже решено

- **Вид правил — оба.** Правило с шаблоном кода проверяет инструмент; правило без шаблона —
  читатель каталога моделью, со сверкой цитат (`catalog.mjs attest`).
- **Пара «дефект / чисто» обязательна.** Без неё гейт правило не грузит. Шаблонное правило
  проверяется на паре при каждом прогоне (бесплатно): обязано сработать на «дефекте» и промолчать
  на «чисто». Правило для модели меряется замером полноты по запросу. Причина — принцип плагина:
  ложная находка дороже пропущенной, а сырое правило даёт ложные находки на каждом прогоне.
- **Источники — проект плюс общие каталоги.** Свои правила лежат в репозитории проекта; в
  `.1c-quality-gate.json` можно подключить ещё каталоги по пути (общий репозиторий правил для
  нескольких проектов). Общее правило пишется один раз.

## Рекомендованный подход (предложен, не одобрен)

Правило — папка: карточка в формате каталога плагина (`Триггер / Почему / Как чинить / Когда это
не дефект`) плюс `defect.*` и `clean.*`. Коды правил проекта — `prj:ИМЯ`; валидатор узнаёт их по
файлам проекта так же, как `qg:` по реестру (`tools/evidence-scopes.mjs`). Шаблонные правила
печатают строку следа и отмечаются в журнале прогонов; модельные входят в `examined` читателя
каталога. Чтение карточек переиспользует `readCatalog(dir)` из `tools/gen-catalog-index.mjs`.

Отвергнуто: правила внутри `.1c-quality-gate.json` (многоабзацная карточка и код в JSON
неудобны); правила как навык Claude в проекте (нет следа, сверки цитат и проверки пары — против
принципа «пропуск проверки обязан оставлять след»).

## Что осталось решить

- Язык шаблона: регулярное выражение по добавленным строкам, маска файлов, исключения («разрешено
  в модуле X»), совпадение рядом («в том же методе, что и вызов Y») — пример выше без последнего
  не выражается.
- Может ли находка правила проекта быть 🔴 и что при этом требует валидатор.
- Кто и как подтверждает находку для подзадачи 3: вопрос после прогона, отдельная команда или
  копилка кандидатов на периодический разбор.
- Как правило проекта попадает в замер полноты (`tests/recall.mjs`) и где хранится результат.
