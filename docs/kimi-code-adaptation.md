# Адаптация 1c-quality-gate под Kimi Code CLI — анализ осуществимости

> Анализ подготовлен 2026-08-20 в сессии Kimi Code по просьбе владельца.
> Это **входная точка для отдельной сессии адаптации**: здесь зафиксированы выводы разведки
> возможностей Kimi Code CLI и предварительный план. Источники фактов о Kimi — официальная
> документация (ссылки внизу), а не память модели.

## Вердикт

Полная адаптация **возможна как настоящий плагин**, а не как набор скриптов с ручным запуском.
У Kimi Code CLI есть собственная система плагинов с манифестом `kimi.plugin.json`,
поддерживающим скиллы, слэш-команды, субагентов, MCP-серверы **и хуки** — включая блокируемое
событие `Stop`, на котором держится вся механика гейта.

## Карта переноса компонентов

| Компонент плагина (Claude) | Эквивалент в Kimi | Переносимость |
|---|---|---|
| `skills/<имя>/SKILL.md` | тот же формат `SKILL.md`, декларируется полем `skills` в `kimi.plugin.json` | почти 1:1. Для директорной формы Kimi **требует** `name` и `description` во frontmatter (у нас уже есть). Для автовызова моделью желательно добавить `whenToUse`. Плейсхолдер `${KIMI_SKILL_DIR}` — аналог пути к навыку |
| `hooks/hooks.json` + `gate-arm.mjs` (PostToolUse) | массив `hooks` в `kimi.plugin.json`, событие `PostToolUse` | работает. У Kimi `PostToolUse` — observation-only (возврат не влияет на поток), но `gate-arm` и не блокирует: он пишет state-файл и выводит контекст. **Проверить:** Kimi observation-only может игнорировать stdout — тогда `additionalContext` до модели не дойдёт, и сообщение «гейт взведён» надо выводить иначе |
| `hooks/gate-check.mjs` (Stop) | событие `Stop`, **блокируемое** (exit 2 + stderr, либо JSON `hookSpecificOutput`) | ключевая механика сохраняется полностью. Семантика Kimi: «модель собирается завершить текущий ход» — совместимо с нашим Stop |
| `commands/gate.md`, `commands/gate-status.md` | поле `commands` в манифесте; вызов как `/<plugin-id>:gate` | работает; команды получают неймспейс плагина, тело — промпт с `$ARGUMENTS` |
| `agents/bsl-verifier.md`, `bsl-scout.md`, `xml-runner.md` | поле `agents` (или каталог `agents/` по соглашению) в манифесте | поддерживается; **формат agent-файлов Kimi сверить отдельно** (frontmatter-поля могут отличаться от Claude) |
| `.mcp.json` (v8std) | поле `mcpServers` в манифесте | работает; MCP плагина включаются после `/reload` |
| `tools/*.mjs` (гейт, валидаторы, линтеры) | без изменений | клиент-нейтральные Node-скрипты без зависимостей; вызываются из хуков и навыков |

## Плюсы платформы Kimi для этого плагина

- **`KIMI_PLUGIN_ROOT`** — хуки плагина получают переменную окружения с корнем плагина
  (аналог `CLAUDE_PLUGIN_ROOT`, но доступен и как env, а не только как `${...}` в hooks.json).
  Это прямо решает проблему резолва `$QG`, которая в Claude-версии требует обходного приёма
  («Путь к инструментам плагина» в навыке `quality-gate`).
- **`session_id` в payload хука** — есть и у Kimi (базовый блок payload: `hook_event_name`,
  `session_id`, `session_title`, `client_type`, `cwd`). Сессионное разделение гейтов
  (`qg-pending.json` по сессиям) сохранится.
- Рабочий каталог хука плагина — корень плагина, поэтому `command` может использовать `./`
  пути внутри плагина.

## Что потребует реальной адаптации (не копипаста)

1. **Payload хуков.** Имена полей `tool_input` и структуру событий сверить по факту
   прогоном реального хука под Kimi (docs показывают пример с `payload.tool_input.command`
   для Bash — похоже на Claude, но нужна эмпирическая фиксация для `Write`/`Edit` и `Stop`).
   Общий парсер вынести в `hooks/_shared.mjs` (там уже чтение payload и корень проекта).
2. **Корень проекта пользователя.** Инструменты ищут `CLAUDE_PROJECT_DIR`, затем подъём до
   `.1c-quality-gate.json` / `.git`. У Kimi в payload хука есть `cwd` — добавить как источник.
3. **Каталог состояния.** Сейчас `.claude/.state/`. Для Kimi естественнее
   `.kimi-code/.state/` либо клиент-нейтральное `.qg/.state/`. Решение влияет на
   «Меры против ложных срабатываний» (журнал `qg-runs.jsonl`) и на инструкции про `.gitignore`.
   При двухклиентском варианте (см. ниже) — либо общий каталог, либо раздельные с явным
   правилом «гейт, взведённый Claude, снимается Claude».
4. **Fail-open семантика хуков Kimi.** Ошибка/таймаут хука = разрешить. Совпадает с нашим
   правилом «внутренняя ошибка хуков — молча exit 0», конфликта нет, но Stop-блокировка при
   падении `gate-check.mjs` молча отпустит сессию — это соответствует нашей же политике
   (хук качества не имеет права ломать работу).
5. **Установка.** Claude: `/plugin marketplace add` + `/plugin install`. Kimi:
   `/plugins install https://github.com/Romandredan/1c-quality-gate` (поддерживаются формы
   URL с веткой/тегом/коммитом). Плагины ставятся **per-user на все проекты** — проектного
   скоупа нет; в не-1С проектах по-прежнему спасает молчание `gate-arm`.
6. **README/INSTALL.** Разделы установки, команд (`/gate` → `/1c-quality-gate:gate`),
   переменных окружения — переписать под оба клиента.
7. **CI.** Добавить контур проверки Kimi-манифеста (валидация полей `kimi.plugin.json`,
   синхронизация версий между тремя манифестами) в `tools/validate-package.mjs` и workflow.

## Два варианта структуры (рекомендация: вариант 1)

### Вариант 1 — двухклиентский монорепозиторий (рекомендован)

В этом же репозитории рядом с `.claude-plugin/plugin.json` лежит `kimi.plugin.json`.
Хуки и инструменты автоопределяют клиента по env (`CLAUDE_PLUGIN_ROOT` / `KIMI_PLUGIN_ROOT`,
`client_type` в payload). Общие `tools/`, `skills/`, `shared/`, `assets/` — один код,
одни тесты, один релизный цикл.

Плюсы: нет дублирования инструментов и чеклистов; правка проверки не требует порта в форк;
соответствует собственному принципу плагина «связь по роли, а не по имени продукта» —
клиент (Claude/Kimi) это та же роль «среда выполнения», как анализатор — роль «статический
анализ».

Минусы: `validate-package.mjs` усложняется; риск регрессии одного клиента при правке
механики под другого — лечится тестами payload-нормализации.

### Вариант 2 — отдельный форк `1c-quality-gate-kimi`

Чище по релизам и issues, но все правки `tools/` и чеклистов придётся портажировать вручную;
через несколько месяцев кодовые базы разойдутся, а это плагин, где воспроизводимость вердикта
— смысл существования.

**Решение владельца (2026-08-20, устно при обсуждении):** вариант 1 — «репозиторий ваш,
так что и форк не нужен — просто ветка/PR с Kimi-поддержкой».

## План первой сессии адаптации (черновик)

1. **Эмпирическая фиксация контрактов Kimi** (до любой правки кода):
   - установить плагин-заглушку локально (`/plugins install <локальный путь>`);
   - записать реальные payload событий `PostToolUse` (для `Write`, `Edit`, `Bash`), `Stop`,
     `SessionStart` в файлы; зафиксировать поля, от которых зависит `hooks/_shared.mjs`;
   - проверить: доходит ли stdout observation-only `PostToolUse` до модели (нужно для
     `additionalContext` от `gate-arm`); если нет — перенести уведомление на `Stop`-хук
     или в ответ `Stop` при первой попытке завершения;
   - проверить формат plugin-агентов (frontmatter agent-файлов Kimi).
2. **Манифест:** `kimi.plugin.json` (skills, commands, agents, mcpServers v8std, hooks).
   Имя/id по правилам Kimi: `[a-z0-9][a-z0-9_-]{0,63}` → `1c-quality-gate` валидно.
3. **Клиент-абстракция в `hooks/_shared.mjs`:** нормализация payload (Claude/Kimi → единая
   внутренняя форма), резолв корня плагина и проекта, выбор каталога состояния.
4. **Скиллы:** проверить frontmatter (добавить `whenToUse` для автовызова), заменить
   клиент-специфичные упоминания (`Skill: quality-gate`, `/gate`) на нейтральные или
   двойные.
5. **Команды и агенты:** адаптировать тела под неймспейс Kimi.
6. **Тесты:** фикстуры payload обоих клиентов; `validate-package.mjs` — проверка
   Kimi-манифеста и синхронизации версий; CI-контур.
7. **Документация:** README (установка под оба клиента), INSTALL.md, этот файл обновить
   по итогам (что подтвердилось, что нет).
