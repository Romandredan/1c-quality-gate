# Порядок выпуска релиза

Тег — это то, что реально устанавливается у пользователей. Запись плагина в
`.claude-plugin/marketplace.json` пиннится на него полем `source.ref`, поэтому `main` остаётся
рабочей веткой, а наружу едет только помеченное дерево.

`/plugin install` не скачивает ассеты GitHub Releases: установщик читает `marketplace.json` и
идёт по указанному в нём источнику. Zip-архивы и бинарники прикладывать не нужно, полезная
нагрузка релиза — описание.

## Нумерация

Номер отвечает на один вопрос: **придётся ли что-то делать руками**. Не «стал ли гейт
строже» — строже он становится в каждом втором релизе, это профильная работа плагина, и
номер, растущий от неё, перестаёт быть сигналом.

| Часть | Когда меняется |
|---|---|
| MAJOR | нужны действия пользователя либо ломаются внешние интеграции: схема `.1c-quality-gate.json`, расположение файлов состояния, удаление или переименование инструмента, команды, навыка, имени проверки (`scope`), смена флагов и кодов возврата CLI, смена способа доставки, расширение области взвода гейта на новые классы файлов |
| MINOR | плагин становится строже или умнее в прежнем контракте: новая проверка, признак, архетип, новое обязательное поле следа, новое условие отказа валидатора, новые пороги по умолчанию |
| PATCH | исправления без изменения вердиктов: документация, тесты, обновление закреплённой версии анализатора, когда находки те же |

Прежняя редакция отдавала MAJOR всему, из-за чего ранее собранный отчёт перестаёт проходить
валидатор. Критерий выглядел строгим, а защищал почти несуществующий сценарий: след живёт
внутри одной сессии — его пишут, проверяют и выбрасывают, никто не прогоняет отчёты
полугодовой давности. Зато под него попадала любая новая проверка, и две мажорные версии
подряд вышли за сутки.

### Переходное окно для новых блокирующих требований

Новое условие, из-за которого гейт перестаёт сниматься, выпускается **в два шага**: сначала
предупреждением (`warn`) с текстом, что именно станет ошибкой, и лишь следующим релизом —
ошибкой. Оба шага MINOR.

Причина в том, что обновление плагина происходит без спроса, а гейт стоит в чужом рабочем
процессе. Требование, ставшее блокирующим в момент установки, читается как поломка
инструмента, а не как найденный дефект, — и первое, что делают с таким инструментом, это
обходят его.

Окно не применяется, когда требование и механизм, который его обслуживает, выходят одним
релизом: предупреждать не о чем, пока проверять было нечем. Такой случай называется в
описании релиза прямо.

**Открытых окон нет.** Последнее, открытое в v3.6.0, закрыто в v3.7.0: три предупреждения
`evidence-validator.mjs` стали ошибкой строгого режима (`--gate`), обычный линт по-прежнему
предупреждает:

- контур `code` запущен, но о проходе `ai-antipatterns` или `platform-antipatterns`
  (каталог антипаттернов) не заявлено записью `applied` или `skipped`;
- заявленный в записи `scope` профиль (`volume`, `archetypes`) ниже того, что по тем же
  файлам сессии вернул бы `computeProfile` — модель вправе поднять глубину, не понизить;
- контур `code` запущен на `L2`, но о слое 2 (ревью логики моделью: субагент `cold-reader` и
  `advisor()`) не заявлено записью `applied` или `skipped` (`scope=logic-review`).

Четвёртое предупреждение v3.6.0 в окно не входило и ошибкой не станет: находка 🔴 или
🟠 из текста отчёта, ни один идентификатор которой не стоит в записи `verdict=violation:<id>`.
Сверка разбирает прозу отчёта, а разбор прозы приближённый — по правилам плагина такая
проверка не блокирует и говорит об этом прямо.

## Чеклист

1. `main` зелёный, работа влита.
2. Выбрать номер по таблице выше. Дальше он записан как `X.Y.Z`.
3. Поднять версию в двух манифестах и переставить пин:
   - `.claude-plugin/plugin.json`, поле `version`;
   - `.claude-plugin/marketplace.json`, поля `version` и `source.ref` (`ref` записывается с
     префиксом: `vX.Y.Z`).
4. Прогнать локально:

   ```bash
   node tests/run-tests.mjs
   node tools/validate-package.mjs
   node tools/gen-signs-map-md.mjs   # если менялся signs-map.json
   node tests/recall.mjs             # полнота читателя каталога не ниже порога; результат
                                      # прикладывается к описанию релиза одной строкой
   ```

   `validate-package.mjs` остановит выпуск, если `version` в манифестах разошлись либо `ref`
   не совпадает с версией.

   Если релиз меняет то, что попадает в след (раздел настройки, измерение, имя проверки),
   живая проверка доводится до снятия гейта: `gate.mjs plan` → отчёт →
   `evidence-validator --gate` → `gate.mjs release`. Взвод и Stop этого не покрывают: в 3.8.0
   они прошли, а валидатор отвергал след каждого проекта с новым разделом `tests`.

   Строка про `recall.mjs` в описании релиза обязана называть замер тем, что он есть:
   полнотой срабатывания триггеров без проверки контр-сигналов по карточке (вызов идёт с
   `--allowedTools ""`, читателю недоступна даже карточка признака) — а не итоговым
   вердиктом контура кода. Сам скрипт печатает эту оговорку в сводке и кладёт её в
   `tests/recall/results/<дата>.json` (`note`, `toolsAllowed`). В описание она переносится
   понятным пользователю языком, но без потери смысла: это полнота срабатывания признаков
   без проверки исключений по карточке, а не итоговая точность ревью кода.
5. Коммит: `chore(релиз): vX.Y.Z`.
6. Аннотированный тег с описанием по шаблону ниже:

   ```bash
   git tag -a vX.Y.Z --cleanup=whitespace -F release-notes.md
   ```

   `--cleanup=whitespace` обязателен: по умолчанию `git tag` вырезает из сообщения строки,
   начинающиеся с `#`, и описание теряет все заголовки Markdown.

   Лёгкий тег (`git tag vX.Y.Z` без `-a`) и пустое сообщение workflow отклонит: релиз без
   описания неотличим от релиза, о котором забыли.
7. Отправить коммит и тег одной командой, чтобы не было окна, в котором манифест уже указывает
   на несуществующий тег:

   ```bash
   git push origin main --follow-tags
   ```

8. Убедиться, что workflow `release` прошёл и релиз создан на GitHub.

## Шаблон описания

Описание пишется в Markdown: GitHub показывает его размеченным, а простой текст с отступами
сливается в сплошные абзацы. Читатель — пользователь плагина, а не его автор, поэтому
описание отвечает на три вопроса: что изменилось в поведении гейта, подтверждено ли это и
нужно ли что-то делать. Устройство тестов, ход рассуждений при исправлении и история
промежуточных вариантов в описание не попадают — они остаются в коммитах и PR.

Номер версии в текст не пишется: он уже стоит в заголовке релиза.

Правила языка. Автор пишет сжато, потому что знает устройство плагина; читатель его не
знает, и сжатый текст для него непрозрачен.

1. **Вступление говорит, что изменилось для пользователя**, а не как это устроено: «все
   инструменты проверки запускаются одной командой», а не «инструментальная фаза
   исполняется через `run`».
2. **Термин плагина поясняется при первом упоминании или заменяется описанием того, что
   происходит.** «Холодный читатель — субагент, который оценивает правку без знания
   замысла»; вместо «черновик следа» и «метрики профиля» — что именно считается и зачем.
3. **Одна мысль на предложение, связная речь.** Телеграфный стиль («Обе версии: след
   принят…») и разговорные обороты («запирает», «отрабатывал», «ничего не сочиняет») не
   используются. Перечень из трёх и более пунктов оформляется списком, а не цепочкой через
   запятую.
4. **Пути, флаги и переменные остаются, только если пользователь их вводит или
   настраивает.** Внутренние имена функций, служебные каталоги и хеши коммитов в описание
   не попадают.

```markdown
<Одно-два предложения: что изменилось для пользователя, меняются ли вердикты, нужны ли
действия. Незатронутые контуры перечисляются одной фразой, а не строкой на каждый.>

## Новое

**<Что появилось, одной фразой.>** <Зачем, как работает с точки зрения пользователя, где
включается или настраивается.>

## Исправлено

**<Симптом, как его видел пользователь.>** <Причина, последствие, что сделано, чем
подтверждено.>

## Замеры

<Строка про `recall.mjs` — со смыслом оговорки из сводки скрипта (см. чеклист, шаг 4). A/B
и другие замеры — таблицей «показатель × версия», с условиями стенда и числом запусков.>

## Совместимость

| | |
|---|---|
| Что перестанет проходить | <«нет» либо перечень> |
| Ломающие изменения | <«нет» либо перечень> |
| Миграция | <«не требуется» либо что поправить в `.1c-quality-gate.json`> |
| Закреплённая версия анализатора | <version из `assets/analyzer/runtime-manifest.json`> |
| Минимальная версия Claude Code | <«без изменений относительно vX.Y.Z» либо версия> |
```

Разделы «Новое», «Исправлено» и «Замеры» опускаются, если им нечего сказать. Таблица
«Совместимость» есть в каждом релизе, все пять строк заполнены. Если непустое значение
не помещается в ячейку, в ячейке пишется «см. ниже», а под таблицей идёт одноимённый
подраздел `###`:

- **Что перестанет проходить** — след или прогон, который принимался предыдущей версией, а
  теперь отвергается: новые обязательные записи, новые условия отказа валидатора,
  ужесточённые пороги. Для каждого — что сделать, чтобы проходило. Строка обязательна в любом
  релизе, который ужесточает проверку, включая MINOR; «нет» пишется явно.
- **Ломающие изменения** — только то, что требует действий пользователя или ломает внешние
  интеграции: схема настройки, расположение состояния, переименования инструментов и имён
  проверок, флаги и коды возврата CLI, способ доставки.

Образцы — описания [v3.11.0](https://github.com/Romandredan/1c-quality-gate/releases/tag/v3.11.0)
и [v3.13.1](https://github.com/Romandredan/1c-quality-gate/releases/tag/v3.13.1).

Строка про анализатор обязательна, даже когда версия не менялась. Вердикт гейта зависит от
движка, и человек, читающий отчёт годичной давности, должен понимать, чем этот отчёт получен.

## Откат

Пока тег не отправлен на remote, он снимается локально:

```bash
git tag -d vX.Y.Z
```

Отправленный тег уже мог быть установлен пользователями. Удалять его не следует: выпускается
следующий патч-релиз, а испорченный помечается в описании нового как непригодный.

## Сдвиг закрепления движков

Версии `bsl-analyzer` и `bsl-context` закреплены в `assets/*/runtime-manifest.json` и
сдвигаются PR, а не самообновлением у пользователя: движок, меняющийся между прогонами,
делает вердикт невоспроизводимым. Разбор — `docs/superpowers/specs/2026-09-12-runtime-bump-design.md`.

Workflow `runtime-bump` раз в неделю (и по кнопке «Run workflow») сравнивает закрепление с
последним релизом автора. Есть новее — переписывает манифест и фразы INSTALL.md
(`node tools/runtime-bump.mjs --engine <движок> --apply`), прогоняет проверки и открывает
PR в ветке `chore/bump-<движок>` с назначением на владельца и запросом ревью. Открытый PR
при следующем релизе обновляется, а не дублируется.

Разовая настройка репозитория, без которой создание PR падает: Settings → Actions →
General → «Allow GitHub Actions to create and approve pull requests».

CI `validate` на PR сдвига запускается, но ждёт одобрения владельца: PR открыт ботом, и
GitHub ставит запуск в статус `action_required`. Одобрить — кнопка «Approve and run» на
вкладке Checks этого PR. До одобрения зелёных проверок у PR нет, а проверки на ubuntu уже
прошли внутри самого `runtime-bump`.

Что делает ревьюер такого PR:

| Движок | Проверка | Где |
|---|---|---|
| `bsl-analyzer` | A/B на корпусе: находки те же или расхождения разобраны | `docs/false-positives-cfe.md`, раздел перехода |
| `bsl-analyzer` | состав диагностик `rules list`: новые, переименованные, исчезнувшие | таблица алиасов в `tools/analyzer-run.mjs`, `assets/analyzer/` |
| `bsl-context` | сервер поднимается и отвечает на машине с платформой | `node tools/platform-context-bootstrap.mjs --status` |
| оба | упоминания старой версии из тела PR: пример следа можно оставить, утверждение о закреплении — нет | по списку в PR |

Сдвиг закрепления при тех же находках — PATCH по таблице выше; изменившиеся находки —
MINOR с разделом перехода в `false-positives-cfe.md`.

Локально, без workflow: `node tools/runtime-bump.mjs --engine analyzer --check` говорит,
есть ли новее (код 3), `--apply` переписывает. Проверка после сдвига та же, что в workflow.

## Что в релиз не кладётся

Бинарник статического анализатора. Он намеренно не входит в пакет: около 60 МБ, три платформы,
LGPL-3.0, закреплённая версия скачивается с релизов автора и сверяется по SHA-256. Приложив его
к своему релизу, репозиторий становится распространителем чужого LGPL-кода и противоречит
[INSTALL.md](INSTALL.md).

Архивы с содержимым репозитория. При источнике `github` их никто не скачивает, а GitHub и так
прикладывает к каждому тегу автоматические `Source code (zip/tar.gz)`.
