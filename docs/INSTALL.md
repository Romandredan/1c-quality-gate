# Установка и настройка

## Требования

| Требование | Зачем | Обязательно |
|---|---|---|
| Claude Code | среда выполнения плагина | да |
| Node.js 18+ | хуки-гейты и утилиты следа | да (идёт с Claude Code) |
| MCP `v8std` | тексты стандартов по номеру | да, объявлен в плагине |
| Python 3.8+ и `lxml` | валидаторы XML метаданных | для контура `xml` |
| Статический анализатор BSL | диагностики кода и метаданных | ставится плагином сам |
| Индекс кода 1С (MCP) | граф вызовов, структура объектов | опционально |
| Справочник API платформы (MCP) | сигнатуры методов | опционально |

Все десять валидаторов XML разбирают файлы через `lxml` — одного интерпретатора им мало:
`pip install lxml`. Без библиотеки они падают с `ModuleNotFoundError`, и контур `xml`
теряет валидацию файлов (сверка «диск ↔ состав» работает на Node и остаётся в строю).

Плагин работает без любого из опциональных компонентов: соответствующий слой пропускается
**с явной записью** в следе прогона (`skipped: reason=analyzer_unavailable` и подобные).
Мощность падает, честность — нет.

Анализатор вынесен в отдельный раздел ниже: он закрывает самую большую долю проверок и
единственный из опциональных компонентов может быть объявлен обязательным для проекта.

## Установка плагина

```
/plugin marketplace add Romandredan/1c-quality-gate
/plugin install 1c-quality-gate
```

Перезапустите сессию: навыки материализуются при старте, а не сразу после установки.

Проверка, что всё встало:

```
/gate-status
```

Ответ «Гейт не взведён» означает, что плагин работает и изменений в файлах 1С пока нет.

## Статический анализатор — установка

Плагин не несёт анализатор в пакете — бинарник весит шестьдесят мегабайт и зависит от
платформы, — но **ставит его сам** при первом прогоне, с проверкой контрольной суммы.
Движка два: основной ставится автоматически, запасной требует Java и указывается вручную.

Запускается он **консольно, а не через MCP**. Причина: гейту нужен воспроизводимый вердикт —
одинаковый вход обязан давать одинаковый выход. MCP отвечает на вопросы модели, и «не спросили»
там неотличимо от «проверили и чисто».

### Вариант A: bsl-analyzer (по умолчанию)

Анализатор на Rust, один бинарник, Java не нужна. Умеет `--incremental --changed-files`:
сужает вывод до изменённых файлов, не теряя контекста конфигурации. Замер на дампе типовой УТ
(12 444 файла): проверка одного изменённого модуля — **1,9 с**.

**Ставить руками ничего не нужно.** При первом прогоне плагин скачивает закреплённую версию
с релизов автора, сверяет SHA-256 и публикует в свой каталог данных. Занимает несколько
секунд, повторяется один раз.

Явно, если не хочется ждать первого прогона:

```bash
node "$QG/tools/analyzer-bootstrap.mjs"          # установить
node "$QG/tools/analyzer-bootstrap.mjs" --verify # пересчитать сумму установленного
```

Установка живёт в `${CLAUDE_PLUGIN_DATA}/analyzer/bsl-analyzer/<версия>/` — этот каталог
переживает обновление плагина, поэтому шестьдесят мегабайт не качаются заново на каждую
версию плагина.

> **Почему не лаунчером автора.** Распространяемый им `bsl-analyzer.exe` — тонкая обёртка,
> которая скачивает рабочий бинарник и дальше **обновляет его сама**. Для гейта это
> недопустимо: движок, меняющийся между прогонами, делает вердикт невоспроизводимым.
> Мы качаем конкретный релиз и сверяем сумму **до** первого запуска — закрепление становится
> фактом, а не проверкой постфактум. Зеркала нет: файл берётся с релизов автора.

Если анализатор уже стоит у вас через лаунчер (`~/.bsl-analyzer/bin/`), плагин возьмёт его и
качать ничего не станет — но версию в этом случае гарантирует лаунчер, а не мы.

Автоустановка отключается `analyzer.autoInstall: false`; тогда без анализатора контур кода
честно уходит в `skipped`.

Бинарники автор публикует для **Windows x64, Linux x64 и macOS arm64**. На других платформах
автоустановка не сработает — поставьте анализатор сами и укажите `analyzer.binary`, либо
переключитесь на движок `bsl-ls`.

Проект называет себя экспериментальным (версия 0.2.x, релизы почти ежедневные). Закреплено и
проверено на **0.2.66**; версия и суммы лежат в `assets/analyzer/runtime-manifest.json`.

### Вариант B: BSL Language Server (запасной)

Зрелый анализатор с большим сообществом; нужна Java 17, 21 или 25. Берите его, если
предсказуемость важнее скорости. Скачайте `bsl-language-server-<версия>-exec.jar` из релизов
`1c-syntax/bsl-language-server` и укажите путь в конфиге. Проверено на **1.0.7**.

Ограничение, из-за которого он не по умолчанию: **сузить область анализа нельзя**. Указание
более узкого каталога молча гасит диагностики, читающие метаданные (проверено: `-w` это не
компенсирует). Поэтому плагин гоняет его от корня конфигурации и фильтрует отчёт сам, а на
типовой конфигурации это полторы-три минуты против двух секунд у варианта A.

### Настройка анализатора

Секция `analyzer` файла `.1c-quality-gate.json` — его плагин создаёт сам при первом взводе
гейта, заводить руками не нужно (см. [CONFIG.md](CONFIG.md)):

```json
{
  "analyzer": {
    "engine": "bsl-analyzer",
    "version": "0.2.66",
    "required": false
  }
}
```

| Поле | Значение |
|---|---|
| `engine` | `bsl-analyzer` (по умолчанию) либо `bsl-ls` |
| `binary` | путь к бинарнику; по умолчанию ищется в `~/.bsl-analyzer/bin/` |
| `jar` | путь к jar — обязателен для `bsl-ls` |
| `version` | закреплённая версия; несовпадение останавливает прогон |
| `required` | `true` — без анализатора гейт не снимается; по умолчанию `false` |
| `autoInstall` | `false` отключает автоустановку; по умолчанию `true` |
| `config` | свой конфиг движка вместо гейтового из состава плагина |

То же можно задать переменными окружения: `QG_ANALYZER_ENGINE`, `QG_ANALYZER_BIN`,
`QG_ANALYZER_JAR`, `QG_ANALYZER_VERSION`, `QG_ANALYZER_REQUIRED`, `QG_ANALYZER_AUTOINSTALL`.

`version`, отличная от закреплённой в манифесте, автоустановку отключает: контрольной суммы
для чужой версии у нас нет, а качать непроверяемое — значит подменить то, что вы закрепили.
Ставьте такую версию сами и указывайте `binary`.

**`required` по умолчанию `false`**: плагин публичный, и у стороннего пользователя анализатора
может не быть — контур честно пишет `skipped`, прогон идёт дальше. В своих проектах ставьте
`true`, тогда отсутствие анализатора не даст закрыть гейт.

### Проверка, что анализатор работает

```bash
node "$QG/tools/analyzer-run.mjs" --sentinel
```

`found` — движок жив и видит метаданные. `not_found` — прогон недостоверен: сломан движок,
испорчен конфиг или потерян контекст конфигурации.

Часовой устроен как фикстура: мини-конфигурация из состава плагина с заведомо неверным
сочетанием флагов общего модуля, на которой обязана сработать `CommonModuleInvalidType`. Она
выбрана потому, что читает **метаданные**: при потере контекста гаснет именно этот класс
проверок, а обычные замечания продолжают приходить, и отчёт выглядит рабочим.

### Состав проекта определяется сам

Перед прогоном плагин находит корень основной конфигурации и корни расширений (различает их
по `<ConfigurationExtensionPurpose>` в корневом XML) и кладёт сгенерированный конфиг
анализатора в `.claude/.state/qg-analyzer.toml`. Настройки диагностик берутся из состава
плагина, состав проекта — из раскладки.

Без этого расширение разбирается в одиночку и не видит ни основной конфигурации, ни БСП:
каждое обращение к `ОбщегоНазначения` становится «неразрешённым вызовом». На боевых
расширениях это была треть всех находок.

> **Первый прогон на большой конфигурации долгий** — около шести минут на 23 тысячах файлов:
> операционная система прогревает файловый кэш. Последующие прогоны — 2–9 секунд, включая
> смену состава расширений. После перезагрузки машины первый прогон снова долгий.

Если основная конфигурация в проекте не найдена (репозиторий одного расширения), анализ идёт
по расширению, а диагностики о неразрешённых именах понижаются до информационных: отличить
«имя из основной конфигурации» от настоящей ошибки в таком режиме нельзя. В следе это
отмечается записью `not_verified: dimension=cross-config-resolution`.

### Неразобранные файлы называются своим именем

Модуль, который анализатор не смог разобрать, выдаёт ошибки разбора сотнями. Показывать их
как находки — значит утверждать, что в файле триста проблем, тогда как по нему не проверено
ничего. Такие файлы выводятся отдельной строкой и попадают в след записью
`not_verified: dimension=static-analysis, reason=parse_failed`.

Известный случай: модуль с `&ИзменениеИКонтроль`, где директивы `#Удаление` и `#Вставка`
стоят внутри многострочного строкового литерала. Для 1С это законный код, лексер анализатора
на нём спотыкается.

### Пороги проекта и пороги гейта разделены

Гейт запускает анализатор со **своим** конфигом (`assets/analyzer/`), проектный продолжает
править IDE. Иначе отключённая в проекте диагностика делала бы гейт тише, и об этом никто бы
не узнал. В гейтовом конфиге выключены только типографика и форматирование — за них отвечает
контур `file-hygiene`.

### Обновление анализатора

Обновляйтесь свободно: плагин связан с движком по роли, а не по именам инструментов. Задеть
его способны три поверхности, и ни одна не отказывает молча:

| Поверхность | Как проявится отказ | Что делать |
|---|---|---|
| Имена диагностик (`bslls:<Код>`) | находка ссылается на код, которого больше нет | поправить упоминание; валидатор следа проверяет форму идентификатора, а не словарь |
| Аргументы консольного режима | анализатор не отвечает → `skipped: reason=analyzer_unavailable` | обновить `tools/analyzer-run.mjs`; деградация отрабатывает сама |
| Имя диагностики часового | часовой уходит в `not_found` и **блокирует снятие гейта** | заметно сразу |

Прежний риск «переименовали ключ в конфиге проекта — гейт молча ослеп» снят по построению:
гейт проектный конфиг анализатора больше не читает.

## Настройка порогов

Создавать ничего не нужно: `.1c-quality-gate.json` появится в корне проекта при первой правке
файла 1С, с пустыми секциями и описанием ключей внутри. Правьте в нём только то, что
отличается от умолчания.

```json
{
  "volume": {
    "c1MaxLines": 40,
    "c1MaxFiles": 1
  },
  "complexity": {
    "maxNesting": 4,
    "maxMethodLines": 120,
    "maxParams": 7
  },
  "archetypes": {
    "custom": [
      { "name": "exchange", "markers": ["ПланОбмена", "ОбменДанными.Загрузка"], "minCode": "L2" }
    ]
  },
  "sentinel": {
    "id": "std454"
  }
}
```

Все поля необязательны — незаданные берут значения по умолчанию. Что действует сейчас и
откуда взято:

```bash
node "$QG/tools/config.mjs" show
```

`sentinel.id` — номер заведомо существующего стандарта, которым проверяется живость сервиса
стандартов. Умолчание `std454`; своё значение имеет смысл задать, если однажды исчезнет
именно эта страница — тогда часовой упадёт во всех проектах разом, а отличить исчезновение
номера от недоступности сервиса будет нечем.

Полный справочник ключей, приоритет источников и поведение при ошибках в файле —
[CONFIG.md](CONFIG.md).

## Как работает гейт

1. Правка `.bsl` или XML метаданных внутри `src/`, `cf/`, `cfe/` взводит маркер в
   `.claude/.state/qg-pending.json` вашего проекта.
2. Попытка завершить сессию блокируется `Stop`-хуком (код возврата 2) со списком файлов.
3. Прогон навыка `quality-gate` формирует отчёт со следом и снимает гейт.

Гейт взводится **всегда**, потому что хук видит одну правку и не может оценить её масштаб.
Градация работает на снятии: прогон класса C0/C1 занимает секунды.

Если правка действительно не требует проверки:

```bash
node "$QG/tools/gate.mjs" release --class C0 --reason "правка комментария"
```

Причина сохраняется в `.claude/.state/qg-done.json`. Для классов C2 и C3 такое снятие
запрещено — нужен полноценный прогон. Заявленный класс сверяется с реальным охватом:
объявить косметикой правку трёх и более файлов не получится.

### Параллельные сессии

Состояние гейта разделено по сессиям, и это не деталь реализации, а необходимость: в одном
проекте нередко работают две сессии сразу. Каждая отвечает только за свои правки.

- Завершение блокируется **только** за файлы текущей сессии.
- Правки другой сессии показываются информационной строкой, но не блокируют.
- `release` снимает гейт своей сессии; чужие остаются взведёнными.
- Когда сессий несколько, указывайте `--session <id>` — идентификатор печатается в
  сообщении о блокировке.

Снимать чужой гейт нельзя: это объявляет проверенной работу, которой вы не видели.

## Добавьте состояние гейта в .gitignore

```gitignore
.claude/.state/
.qg-analyzer/
```

Первое — рабочее состояние сессии, а не артефакт проекта. Второе — временный каталог отчёта
запасного движка: он создаётся рядом с исходниками (системный TEMP на Windows живёт на C:, и
при проекте на другом диске BSL Language Server падает с невнятным `'other' has different
root`) и убирается сам, но переживёт аварийное завершение.

`.1c-quality-gate.json` в список **не входит**: пороги и архетипы — общая настройка команды,
её коммитят.

## Диагностика

**Гейт не взводится.** Проверьте, что файл попадает под правила: `.bsl`/`.os` в любом месте,
`.xml` внутри `src/`, `cf/`, `cfe/` либо `Configuration.xml`. Файлы вне 1С игнорируются
намеренно — в не-1С проектах плагин молчит.

**Завершение заблокировано, а прогон уже был.** Гейт снимает только `tools/gate.mjs release`.
Если прогон прервался и отчёт не сформирован, маркер остаётся — так и задумано.

**Валидатор отклоняет след.** Прочитайте сообщение: оно называет строку и конкретное
нарушение. Частые случаи — пустой список идентификаторов, отсутствие записи `sentinel` и
полностью чистый вердикт без записи `not_verified`.

**Гейт мешает в чужом проекте.** Отключите плагин для конкретного проекта через `/plugin`
либо удалите маркер вручную: `.claude/.state/qg-pending.json`.
