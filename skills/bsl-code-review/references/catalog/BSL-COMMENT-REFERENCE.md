## Триггер

Комментарий ссылается на задачу, решение владельца или проектный документ.

## Почему

Номер задачи, «решение владельца», ссылка на раздел проектного документа попадают в код вместе
с рассуждением, которое к ним прилагалось на обсуждении. Нужно это рассуждение тому, кто решение
пересматривает, а читает его каждый, кто открывает метод. Через полгода задача закрыта, документ
переименован, и комментарий ссылается в никуда.

## Как чинить

#### Неправильно

```bsl
// Третья проверка - основание команды перед отправкой (задача 10.6): отменённое или
// изменённое основание (решение владельца 21.09, design.md Р-23) не отправляется.
```

#### Правильно

```bsl
// Отменённое или изменённое основание не отправляется: шлюз вернул бы деньги по документу,
// которого в учёте уже нет.
```

В коде остаётся то, что код делает, и причина, по которой он не делает очевидного (#std453).
История решения переносится в документ решений контура.

## Когда это не дефект

- ссылка на стандарт (`#std453`) или на метод («См. ОбщийМодуль.Метод») — это не история
  решения, а указатель, который живёт вместе с кодом;
- ссылка на внешний протокол, без которой поле не понять (номер раздела спецификации внешнего
  API) — метка там не срабатывает, если не совпадает с шаблоном проекта.

## Что проверяет инструмент

Проверка: `qg:BSL-COMMENT-REFERENCE` (`tools/bsl-lint.mjs`), 🟡, подсказкой — строка
комментария совпадает с меткой: «задача N», «решение владельца», «ревью», `openspec`,
`design.md` и другие имена проектных файлов, `.yaml:N`, `ADR-N`. Проверяются изменённые
методы вместе с описанием над ними. Список меток проект заменяет ключом
`bslLint.commentMarkers`.

**Чего не ловит.** Рассуждение без меток: длинное обоснование, перенесённое из обсуждения без
номера задачи, инструмент не увидит. Слово «спецификация» меткой не считается: в коде 1С это
чаще предметный термин (ресурсная спецификация), чем документ разработки.
