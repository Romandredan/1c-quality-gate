# Порядок выпуска релиза

Тег — это то, что реально устанавливается у пользователей. Запись плагина в
`.claude-plugin/marketplace.json` пиннится на него полем `source.ref`, поэтому `main` остаётся
рабочей веткой, а наружу едет только помеченное дерево.

`/plugin install` не скачивает ассеты GitHub Releases: установщик читает `marketplace.json` и
идёт по указанному в нём источнику. Zip-архивы и бинарники прикладывать не нужно, полезная
нагрузка релиза — описание.

## Нумерация

Номер отвечает на один вопрос: **придётся ли что-то делать руками**. Не «стал ли гейт
строже» — строже он становится в каждом втором релизе, это профильная работа плагина, и
номер, растущий от неё, перестаёт быть сигналом.

| Часть | Когда меняется |
|---|---|
| MAJOR | нужны действия пользователя либо ломаются внешние интеграции: схема `.1c-quality-gate.json`, расположение файлов состояния, удаление или переименование инструмента, команды, навыка, имени проверки (`scope`), смена флагов и кодов возврата CLI, смена способа доставки, расширение области взвода гейта на новые классы файлов |
| MINOR | плагин становится строже или умнее в прежнем контракте: новая проверка, признак, архетип, новое обязательное поле следа, новое условие отказа валидатора, новые пороги по умолчанию |
| PATCH | исправления без изменения вердиктов: документация, тесты, обновление закреплённой версии анализатора, когда находки те же |

Прежняя редакция отдавала MAJOR всему, из-за чего ранее собранный отчёт перестаёт проходить
валидатор. Критерий выглядел строгим, а защищал почти несуществующий сценарий: след живёт
внутри одной сессии — его пишут, проверяют и выбрасывают, никто не прогоняет отчёты
полугодовой давности. Зато под него попадала любая новая проверка, и две мажорные версии
подряд вышли за сутки.

### Переходное окно для новых блокирующих требований

Новое условие, из-за которого гейт перестаёт сниматься, выпускается **в два шага**: сначала
предупреждением (`warn`) с текстом, что именно станет ошибкой, и лишь следующим релизом —
ошибкой. Оба шага MINOR.

Причина в том, что обновление плагина происходит без спроса, а гейт стоит в чужом рабочем
процессе. Требование, ставшее блокирующим в момент установки, читается как поломка
инструмента, а не как найденный дефект, — и первое, что делают с таким инструментом, это
обходят его.

Окно не применяется, когда требование и механизм, который его обслуживает, выходят одним
релизом: предупреждать не о чем, пока проверять было нечем. Такой случай называется в
описании релиза прямо.

**Открытые окна на момент v3.6.0.** Три предупреждения `evidence-validator.mjs`, введённые
этим релизом, станут ошибкой (`--gate`) в следующем MINOR:

- контур `code` запущен, но о проходе `ai-antipatterns` или `platform-antipatterns`
  (каталог антипаттернов) не заявлено записью `applied` или `skipped`;
- заявленный в записи `scope` профиль (`volume`, `archetypes`) ниже того, что по тем же
  файлам сессии вернул бы `computeProfile` — модель вправе поднять глубину, не понизить;
- контур `code` запущен на `L2`, но о слое 2 (ревью логики моделью: `advisor()` и холодный
  читатель) не заявлено записью `applied` или `skipped` (`scope=logic-review`).

Описание релиза следующего MINOR обязано назвать все три пункта в разделе «Что перестанет
проходить».

## Чеклист

1. `main` зелёный, работа влита.
2. Выбрать номер по таблице выше. Дальше он записан как `X.Y.Z`.
3. Поднять версию в двух манифестах и переставить пин:
   - `.claude-plugin/plugin.json`, поле `version`;
   - `.claude-plugin/marketplace.json`, поля `version` и `source.ref` (`ref` записывается с
     префиксом: `vX.Y.Z`).
4. Прогнать локально:

   ```bash
   node tests/run-tests.mjs
   node tools/validate-package.mjs
   node tools/gen-signs-map-md.mjs   # если менялся signs-map.json
   node tests/recall.mjs             # полнота читателя каталога не ниже порога; результат
                                      # прикладывается к описанию релиза одной строкой
   ```

   `validate-package.mjs` остановит выпуск, если `version` в манифестах разошлись либо `ref`
   не совпадает с версией.

   Строка про `recall.mjs` в описании релиза обязана называть замер тем, что он есть:
   полнотой срабатывания триггеров без проверки контр-сигналов по карточке (вызов идёт с
   `--allowedTools ""`, читателю недоступна даже карточка признака) — а не итоговым
   вердиктом контура кода. Сам скрипт печатает эту оговорку в сводке и кладёт её в
   `tests/recall/results/<дата>.json` (`note`, `toolsAllowed`), так что переформулировать
   её вручную не нужно — переносится готовый текст.
5. Коммит: `chore(релиз): vX.Y.Z`.
6. Аннотированный тег с описанием по шаблону ниже:

   ```bash
   git tag -a vX.Y.Z -F release-notes.txt
   ```

   Лёгкий тег (`git tag vX.Y.Z` без `-a`) и пустое сообщение workflow отклонит: релиз без
   описания неотличим от релиза, о котором забыли.
7. Отправить коммит и тег одной командой, чтобы не было окна, в котором манифест уже указывает
   на несуществующий тег:

   ```bash
   git push origin main --follow-tags
   ```

8. Убедиться, что workflow `release` прошёл и релиз создан на GitHub.

## Шаблон описания

```text
vX.Y.Z

Контуры
  code:     <что изменилось>
  arch:     <что изменилось>
  xml:      <что изменилось>
  hygiene:  <что изменилось>
  оркестратор: <что изменилось>

Что перестанет проходить
  <след или прогон, который принимался предыдущей версией, а теперь отвергается: новые
   обязательные записи, новые условия отказа валидатора, ужесточённые пороги. Для каждого —
   что сделать, чтобы проходило. Раздел обязателен в любом релизе, который ужесточает
   проверку, включая MINOR; «Нет» пишется явно>

Ломающие изменения
  <только то, что требует действий пользователя или ломает внешние интеграции: схема
   настройки, расположение состояния, переименования инструментов и имён проверок, флаги и
   коды возврата CLI, способ доставки>

Миграция
  <что поправить в .1c-quality-gate.json>

Закреплённая версия анализатора
  <version из assets/analyzer/runtime-manifest.json>

Минимальная версия Claude Code
  <указывать, только если задействованы новые возможности плагинов>
```

Раздел про анализатор обязателен даже когда версия не менялась. Вердикт гейта зависит от
движка, и человек, читающий отчёт годичной давности, должен понимать, чем этот отчёт получен.

## Откат

Пока тег не отправлен на remote, он снимается локально:

```bash
git tag -d vX.Y.Z
```

Отправленный тег уже мог быть установлен пользователями. Удалять его не следует: выпускается
следующий патч-релиз, а испорченный помечается в описании нового как непригодный.

## Что в релиз не кладётся

Бинарник статического анализатора. Он намеренно не входит в пакет: около 60 МБ, три платформы,
LGPL-3.0, закреплённая версия скачивается с релизов автора и сверяется по SHA-256. Приложив его
к своему релизу, репозиторий становится распространителем чужого LGPL-кода и противоречит
[INSTALL.md](INSTALL.md).

Архивы с содержимым репозитория. При источнике `github` их никто не скачивает, а GitHub и так
прикладывает к каждому тегу автоматические `Source code (zip/tar.gz)`.
