# Сходимость проходов гейта: дизайн

Статус: **утверждено 1 октября 2026**, к реализации в два выпуска — v3.16.0 и v3.17.0.

## Задача

Гейт проверяет правку целиком при каждом запуске, а любая правка после проверки требует
нового полного запуска. На рабочем проекте это дало цикл «проход → исправить найденное →
проход», который не сходится. По журналам сессий за 21–30 сентября:

- в одной сессии 27 проходов, из них 15 запущены самой сессией после исправления находок
  прошлого прохода, без единого сообщения пользователя между ними;
- самая длинная серия — девять проходов подряд по одному модулю, по 40 минут каждый; ни в
  одном отчёте нет находки 🔴, то есть гейт можно было снять после любого из них;
- число открытых записей о нарушениях за серию держалось между 12 и 15, а правка выросла
  с +176 до +474 строк: исправления по 🟡 в нетронутых правкой строках добавляли код, который
  владелец затем назвал лишним и два прохода потратил на откат;
- две из восьми 🟠 серии внесли сами исправления предыдущего прохода — повторная проверка
  исправления нужна; три 🟡 нашлись в коде, который прошлые проходы читали без замечаний, —
  субагент каждый раз читает всю правку заново и находит другое.

Итого 754 минуты работы субагента в одной сессии, большая часть — на повторы.

## Решения владельца

1. Автономность сохраняется: первый круг исправлений полный — сессия исправляет 🔴, 🟠 и 🟡
   сама. Человек подключается в конце: по 🔴 без безопасного исправления и по находкам, для
   которых модель не может оценить, дефект ли это и насколько он важен.
2. Находки в коде, которого правка не касалась, в этом цикле не исправляются: они попадают
   в список техдолга, решение по ним — владельца.
3. Итог гейта доходит до пользователя в чате: остаток находок в правке, список вне правки и
   то, что требует решения.
4. Повторный проход проверяет исправления, а не читает правку заново.

## Понятия

| Термин | Значение |
|---|---|
| Цикл | От взвода гейта сессии до снятия. Новая правка после снятия открывает новый цикл. |
| Проход | Один запуск проверки внутри цикла, начинается командой `gate.mjs run --session`. Не больше трёх на цикл. |
| Снимок | Содержимое файлов сессии на момент старта прохода: хеш blob каждого файла (`git hash-object -w`). |
| База прохода | То, от чего считается разница: `HEAD` для первого прохода, снимок предыдущего — для следующих. |
| Правка | Разница между HEAD и рабочим деревом по файлам сессии: весь объём работы цикла, независимо от номера прохода. |
| Находка в правке | Строка находки попадает в метод BSL, задетый правкой (`analyzeChangedMethods`), либо в диапазон строк XML из hunk'ов разницы с HEAD. |
| Находка вне правки | Любая другая находка в файлах сессии. |
| Остаток | Открытые находки последнего отчёта цикла: в правке, вне правки, требующие решения. |

«В правке» всегда считается относительно HEAD, а не относительно базы прохода: исправление,
сделанное на втором круге, остаётся частью правки.

## Процесс глазами модели

1. **Первый проход** — полный, база `HEAD`. Как сейчас.
2. **Круг исправлений.** Сессия исправляет все открытые находки в правке, с которыми согласна.
   Несогласие с находкой записывает в описании работы (пункт 4) с причиной — следующий проход
   проверяет причину по коду, а не принимает на веру. Находки вне правки сессия не трогает.
3. **Проход по исправлению** — база «снимок прошлого прохода». Инструменты идут по файлам
   целиком: они детерминированы и стоят секунды. Модельные слои получают разницу от базы и
   список находок прошлого отчёта: проверяют, что каждая закрыта или отклонена обоснованно, и
   читают только новые строки. Старый код заново не читается — случайные новые находки в уже
   проверенном коде исчезают по построению.
4. **Второй круг** закрывает то, что внесли исправления. Третий проход — последний в цикле.
5. **Потолок.** Четвёртый `run` в цикле отказывает без `--decision "<кто решил и что>"`.
   Сообщение пользователя сбрасывает счёт: после него проходы считаются заново, а снимки
   остаются — база следующего прохода по-прежнему последний снимок.
6. **Снятие.** Без 🔴 в правке гейт снимается по отчёту. Остаток переносится в журнал снятий.
   Сессия заканчивает работу сообщением с тремя списками: исправлено за цикл; остаток в
   правке с её оценкой; вне правки и требующее решения. Stop-хук при первом завершении после
   снятия печатает пользователю служебное сообщение со счётом остатка по уровням и путём к
   отчёту — независимо от текста модели.
7. **Решение владельца** требуется в двух точках: 🔴 в правке, который модель не берётся
   исправить (как сейчас — `release --critical-decision`), и раздел «Нужно решение» отчёта.

## Состояние

Сессия в `qg-pending.json` получает поле `cycle`; файл — поле `checked`.

```json
{
  "cycle": {
    "passes": [
      { "n": 1, "startedAt": "…", "base": "HEAD", "blobs": { "<rel>": "<sha>" },
        "report": "<путь принятого отчёта>", "acceptedAt": "…" }
    ],
    "decisions": [ { "at": "…", "pass": 4, "text": "<кто решил и что>" } ],
    "userPromptAt": "…"
  },
  "files": {
    "<rel>": { "…": "как сейчас", "checked": { "blob": "<sha>", "pass": 1 } }
  }
}
```

- `run --session` добавляет запись прохода: номер — число записей плюс один; `blobs` —
  снимок на момент старта; `base` — `HEAD` для первого прохода и для файла, у которого нет
  `checked` (добавлен в сессию после прошлого прохода), иначе `pass:<n−1>`.
- `evidence-validator --gate --session <id> <отчёт>`, приняв отчёт, записывает в последний
  проход `report` и `acceptedAt` и ставит файлам `checked = { blob, pass }` из `blobs` прохода.
  Если текущий blob файла отличается от `blobs` — файл менялся во время прохода: валидатор
  предупреждает и `checked` этому файлу не ставит; следующий проход считает его от прошлой базы.
- Взвод файла (`armGate`) поле `checked` не трогает: оно описывает, что проверено, а не что
  актуально; актуальность определяет сравнение blob при следующем `run`.
- `release` переносит `cycle` и остаток в запись журнала снятий; `cycle` в снятой сессии
  закрывается. Новый взвод после снятия начинает новый цикл без `checked`.
- Хук `UserPromptSubmit` (новая запись в `hooks/hooks.json`) пишет `cycle.userPromptAt`, если
  состояние есть и сессия в нём взведена; в чужих проектах он не делает ничего. Счёт проходов
  для потолка — записи с `startedAt` позже `userPromptAt`.
- Все записи — под замком состояния, как остальные писатели.

Файл без `checked` на втором проходе, blob которого равен снимку прошлого прохода
(не менялся), получает в выводе `run` пометку «не менялся с прохода N» — его слои закрываются
существующим `skipped reason=verified_earlier`.

## Разница от базы

`tools/profile.mjs`: `diffFile` получает базу. Для `HEAD` — как сейчас. Для снимка — текущий
blob (`git hash-object -w`) и `git diff --numstat -U0 <снимок> <текущий>`; заголовки hunk'ов
дают строки рабочего дерева, как и сейчас. Снимок, которого нет в хранилище объектов (убран
сборкой мусора), — база `HEAD` с пометкой `note: 'base_missing'` в профиле и в выводе `run`.
Файл вне git — как сейчас, `no_git`, каждый проход полный.

Профиль прохода по исправлению считается от базы прохода. Строка `scope` получает поле
`base=HEAD|pass:<n>`: `pass:<n>` означает «снимок прохода n у файлов, которые он проверил;
HEAD у файлов, добавленных в сессию позже» — такие файлы `run` называет отдельно. Валидатор в
режиме `--gate --session` пересчитывает профиль по состоянию сессии с той же базой для каждого
файла, правило «профиль можно поднять, нельзя понизить» сохраняется. Без `--session` при
`base≠HEAD` валидатор предупреждает, что базу сверить не по чему.

**Дополнение 5 октября 2026 (решение владельца).** Глубина прохода по исправлению не опускается
ниже глубины прохода, от снимка которого считается разница, если исправление по этой разнице
значительнее правки одного метода (объём C2 и выше). Обоснование владельца: любое исправление
может нарушить общую логику кода, и если правка поднимала вопрос архитектуры, после исправления
её нужно проверить заново. Проход записывает свою глубину (`resolved`), `run` поднимает до неё
`code` и `arch` и печатает строку «глубина code и arch сохранена от прохода K»; слой 2 и контур
`arch` получают и всю правку (`change.diff`). Исправление в пределах одного метода идёт на своей
глубине.

## Классификация находок

`run` печатает для каждого файла таблицу «Задето правкой»: методы с диапазонами строк (BSL) или
диапазоны hunk'ов (XML) относительно HEAD, на любом проходе. Находки инструментов `run`
помечает сам: в правке или вне её — по строке. Находки модельных слоёв помечает субагент по той
же таблице. Находка без строки считается в правке: ошибка в громкую сторону.

Находка вне правки не блокирует снятие на любом уровне, включая 🔴: критический дефект в
коде, которого правка не касалась, помещается не в раздел «Вне правки», а первым пунктом
раздела «Нужно решение» — владелец видит его в итоге, но в чужой задаче он не исправляется и
гейт не держит. Обратное правило столь же жёсткое: 🔴 в правке никогда не попадает в «Нужно
решение» — он остаётся в «Открыто в правке» и снимается только исправлением или
`--critical-decision`, как сейчас.

## Отчёт субагента

Разделы находок вместо одного списка:

| Раздел | Содержание |
|---|---|
| `## Закрыто` | Находки прошлого отчёта, закрытие которых проверено по коду; отклонённые автором — с оценкой причины. Только с второго прохода. |
| `## Открыто в правке` | Находки по уровням 🔴 / 🟠 / 🟡 с идентификаторами — как сейчас. |
| `## Вне правки` | Находки любого уровня в нетронутом коде. |
| `## Нужно решение пользователя` | Находки, где субагент не может оценить, дефект ли это и насколько он важен: уровень «вопрос», низкая уверенность, зависимость от данных или договорённостей. |
| `## Отклонённые кандидаты` | Как сейчас. |

Валидатор исключает разделы «Вне правки» и «Нужно решение пользователя» из блокирующих
находок тем же механизмом, что «Отклонённые» (`NOT_FINDINGS`), и не требует для них покрытия
записями `verdict=violation`. Правило из предыдущего раздела — 🔴 в правке не бывает в «Нужно
решение» — обязанность субагента; она закрепляется в агенте и проверяется тестом полноты
правил, валидатор по прозе её не проверяет.

Вердикт называет уровни и числа: «есть замечания: 🟠 1, 🟡 4; вне правки 3; нужно решение 1».
Формулировка «находка блокирует вердикт „Чисто“» из навыка и агента уходит.

Ответ субагента основной сессии дополняется строками `Проход: N из 3, база: …`, `Закрыто: N из
M`, `Вне правки: N`, `Нужно решение: N`.

## Основная сессия

Текст передачи (`handoffLines`) получает пункт 8 — для прохода по исправлению: по каждой
находке прошлого отчёта, исправлена ли и как либо почему нет. Путь к прошлому отчёту субагент
берёт из вывода `run`, а не из пересказа.

Сообщение блокировки и подсказка при взводе называют номер прохода, который запустит
проверка, и потолок: «правка после прохода 2 потребует прохода 3 из 3». После третьего —
прямой текст: «потолок цикла; дальше либо снятие с остатком, либо `--decision`».

Правило о находках вне правки и о трёх списках в завершающем сообщении живёт в тексте
передачи: субагент сессии не видит, и единственный канал к ней — этот текст.

## Снятие и итог

`release --evidence <отчёт>` разбирает разделы последнего отчёта и записывает в журнал снятий
`residual`: открытые в правке по уровням, вне правки, требующие решения — заголовки находок с
идентификаторами. Печатает их же в выводе. `--decision` потолка и `--critical-decision`
записываются рядом.

Stop-хук: если у сессии есть запись в журнале снятий с `residual` и без `relayedAt`, печатает
`systemMessage` вида «Гейт сессии снят. Остаток в правке: 🔴 0, 🟠 1, 🟡 4; вне правки 3; нужно
решение 1. Отчёт: <путь>» и ставит `relayedAt`. Это страховка на случай, когда модель списки
сократила; основной канал — завершающее сообщение сессии по тексту передачи.

В OpenCode `systemMessage` нет: итог уходит сообщением плагина на `session.idle` один раз, по
той же записи журнала.

## Что не меняется

Взвод, разделение по сессиям, отпечатки и отказ от файла (v3.15.0), журнал прогонов,
отметки `verify`, состязательный аудит, правила снятия при 🔴 в правке.

## Границы

- Проход по исправлению не находит дефекты старого кода, пропущенные первым проходом: это
  решение владельца, второй независимый взгляд остаётся состязательным аудитом по запросу.
- Снимок живёт в хранилище объектов git как недостижимый blob; сборка мусора может его
  убрать после срока хранения (по умолчанию две недели). Пропавший снимок даёт полный проход
  с пометкой, а не ошибку.
- Сброс счёта по сообщению пользователя в OpenCode зависит от того, получает ли плагин событие
  нового сообщения; если нет — потолок действует без сброса, и это сказано в `docs/OPENCODE.md`.
- Классификация XML по строкам hunk'ов приближённая: находка по элементу, часть строк которого
  тронута, считается в правке.

## Проверка

- Тесты: записи прохода и снимки; выбор базы по файлам; потолок и `--decision`; сброс по
  `UserPromptSubmit`; разница от blob в `profile.mjs`; `scope base` и пересчёт валидатором;
  исключение раздела «Вне правки»; `residual` в журнале; сообщение Stop-хука один раз;
  полнота правил навыка и агента (строки о разделах и о классификации не исчезли).
- A/B агента и навыка до выпуска по правилу памяти: стенд с одной правкой — полный проход,
  исправление, проход по исправлению; сравнение вызовов инструментов, минут и состава находок
  со старой версией.
- Замер на рабочем проекте после выпуска по журналам: проходов на цикл, минут на цикл, прирост
  строк правки между проходами. Цель — не больше трёх проходов на цикл по построению и прирост
  правки от исправлений, не выходящий за задетые методы.

## Выпуск

**v3.16.0** — разделы отчёта и классификация «в правке / вне правки», потолок с `--decision`,
хук `UserPromptSubmit`, остаток в журнале и в чате, тексты передачи и блокировки. Закрывает
рост правки от чужого кода и даёт владельцу итог; проходы остаются полными.

**v3.17.0** — снимки, база прохода, разница от blob, модельные слои по разнице, раздел
«Закрыто», `scope base` в валидаторе. Убирает повторное чтение.

Оба — MINOR: новое поведение в прежнем контракте, новые поля состояния и следа необязательны
для прежних отчётов.
